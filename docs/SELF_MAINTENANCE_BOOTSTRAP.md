# Split self-maintenance: Candidate-local Codex executor

Source repository: Public Engine. Canonical maintenance command/report/Goal/Owner records: Private State. Proposed maintenance workdir: an independent Engine-maintenance clone, never running Engine, State, or a linked worktree sharing authority. No extra daemon or repository synchronization protocol is needed.

**Split self-maintenance execution is admitted only after independent-clone preflight, and unattended adoption remains disabled.** Ordinary Bridge commands keep the existing full-access Codex mode. A self-maintenance run ignores ambient user config and execpolicy rules, explicitly selects the elevated Windows backend, fixes approval policy to `never`, and selects the built-in `:workspace` permission profile directly. The validated Candidate is the complete maintenance source tree. Built-in `:workspace` keeps Candidate and ordinary system temporary directories writable while preserving protected workspace paths such as `.git` as read-only. Direct reads from the running Engine, Private State, Legacy, or other host project directories are not part of the maintenance-Agent contract, and the maintenance Agent does not require network access. The outer Worker/Launcher owns production reads, task/context preparation, GitHub interaction, commit/push, restart, and controlled adoption. No legacy `--sandbox`, `-C`, `--cd`, or `--add-dir` authority is admitted. Manual controlled adoption still requires both an operator-installed Private State `worker/deployment.local.json` binding and the outer Launcher's explicit `--allow-controlled-adoption` startup flag.

The candidate-generation workflow is an unattended Codex run inside the Candidate workspace using only local Candidate context supplied by the outer Worker, followed by the existing post-run identity/protected-path guard, CI and independent review. After an operator accepts a candidate, installs the exact deployment binding and explicitly arms the outer Launcher, the existing manual handoff consumer may perform controlled adoption from independently prepared handoff evidence while admissions are drained; its restart evidence lives under State runtime and replacement Workers are explicitly rebound to the same State root. Running Engine and State remain protected paths. A candidate may edit only its independent Engine workdir. State validation must run from an accepted immutable Engine SHA chosen outside the candidate's control; it cannot self-approve by changing its own validator and reference together.

The source package proves run-local policy selection and fail-closed argv construction, but actual native-Windows `:workspace` enforcement still needs host acceptance before this phase is treated as production-complete. No fallback to full access is permitted for a self-maintenance run. System TEMP write access is intentional disposable scratch, not a failure condition. Direct production reads and network access are intentionally outside the maintenance-Agent acceptance contract. Protected Candidate `.git` remains outside the maintenance Agent's mutation authority, so production reads, Git operations and deployment stay with the trusted outer authority. Ordinary non-maintenance projects retain their existing full-access execution model.

Engine rollback with the same compatible State schema must preserve canonical State and local recovery evidence. Rollback to an old combined repository is different: after any canonical mutation, stale combined-repository State is not a lossless rollback target. Never copy State backward or rewind generation automatically.

## Operational evidence checklist

- **Before controlled adoption:** record the independent Candidate and base identities, accepted Candidate SHA, current main SHA and known-good SHA, the fixed canonical State binding, completed drain with no active runs, and the rollback/restart evidence reference or location. Do not add private identifiers or invented evidence.
- **During probation:** verify the replacement Worker identity and record the terminal handoff result. On failure, preserve the same State and use a forward rollback.
- **After rollback:** a fresh adoption uses rollback main as its base, a new independent Candidate, and a new attempt/command identity.

Unattended adoption remains disabled. This checklist records required evidence; it does not claim that deployment has completed.
